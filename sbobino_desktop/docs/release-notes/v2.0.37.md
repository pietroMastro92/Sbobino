## Sbobino 2.0.37

### Fixes

- Companion pairing now survives a Desktop restart: the TLS pairing record is encrypted at rest, bound to the app identity and the active profile, and is removed only by an explicit revoke instead of silently expiring.
- The Companion panel no longer shows a stale model or runtime state after models change; health, readiness and diagnostics are re-read so a previous session cannot describe the current one.
- Diarization readiness now reports one code from a closed set (`no_backend`, `fluid_missing`, `pyannote_missing`, `pyannote_repair_required`, `pyannote_receipt_required`, `pyannote_arch_mismatch`, `device_unsupported`, `ok`) with a static message, and rejects a `diarization=true` job early instead of accepting it and failing after the transcript is saved.
- The Pyannote packaging path sanitizes and re-audits the portable runtime before writing a release zip, so a host Homebrew rpath causes packaging to fail before the archive is written; the same strict audit is shared by the generator, the packager and the repair script.
- Runtime validation for the packaged Pyannote assets now matches the layout that is actually shipped, including the macOS embedded CPython layout used by the release archives.

### New and improved

- Companion is part of the desktop product: an opt-in LAN server with TLS, certificate pinning and bearer pairing that accepts iPhone audio jobs, exposes authenticated health, job and cancellation routes, and revokes a pairing from General settings.
- Chat v2 accepts conversation history supplied by the iPhone for follow-up questions. Health advertises `request_versions: [1, 2]`; answers include validated source citations, and the iPhone acknowledges each delivered answer after saving it.
- AI providers stay explicit and local to the Mac: Apple Foundation Models on supported hardware, or Qwen through a local Ollama endpoint. When the user selects the Mac, the iPhone sends the selected content and prompt for generation on that Mac.
- Speaker turns are measured: diarization results carry `speaker_turns_v1` with measured turn boundaries, and attribution stays conservative, leaving ambiguous or overlapping segments unattributed instead of guessing a speaker.
- Companion health exposes diarization readiness before upload, allowing an updated iPhone client to explain a missing or repairing runtime before sending audio.

### Compatibility

- The product identity remains `com.sbobino.desktop`, and updater artifacts stay signed with the configured key and published through the `public` release profile.
- Native targets remain macOS arm64 and macOS Intel, plus the Windows x86_64 installer; the Linux job keeps its declared frontend and crate validation scope.
- Existing settings, transcripts, artifacts, models and compatible runtimes are preserved across the update.
- The official build uses its own application identity, so a pairing created against a LAN test build does not carry over: pair the iPhone once more through the Companion panel and do not copy tokens, certificates or keys from a test profile.
- Companion is opt-in and off by default; no firewall, VPN or network rule is changed by installing or updating this version.

### Known issues

- Companion is a LAN feature of the desktop app. This release does not ship an App Store build of the iPhone companion and does not guarantee a remote relay outside the local network.
- Local AI generation depends on the Mac: Apple Foundation Models need supported hardware, and Qwen needs a separately installed local Ollama runtime. No iPhone model is bundled or required.
- macOS packages are signed ad hoc and are not notarized unless Developer ID secrets are present in the release environment; Windows installers remain unsigned. Only updater artifacts use the configured updater signature.
- The strict Pyannote portability audit is proven on a sanitized macOS arm64 runtime; the macOS Intel and Windows runtime archives are validated by their own first hosted run and may fail the audit by design.
- Native iPhone pairing, AI generation and interactive accessibility flows are verified on candidate builds, not on the public 2.0.37 artifacts; the public-asset checks remain the release gate.
